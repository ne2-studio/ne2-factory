# Integration and distribution smells

El Baúl is currently a monolithic API plus independently deployable frontends (`app/`, `admin/`), not a distributed system of services or a message-driven architecture. These smells describe pressures typical of that shape. Keep them at this catalogue's minimum depth — do not invest in extended notes here — until real evidence (a queue, a second backend service, cross-service sagas) makes one of them concretely applicable. Do not force-fit any of these onto request/response calls between a frontend and the one API.

| id | Smell | Description | Attributes in tension | Candidate movements | Common false positive |
|---|---|---|---|---|---|
| `synchronous-call-chain` | Synchronous call chain | A request crosses a long chain of synchronous service calls. | `consistency`, flow simplicity vs. `resilience`, latency | Asynchrony; events; caching; aggregation; merge services; graceful degradation | A short, bounded chain (frontend → one API → one database) that isn't actually a chain |
| `event-soup` | Event soup | Many low-semantic events circulate with no ownership, no clear contract, and no comprehensible flow. | decoupling vs. `comprehensibility`, `operability` | Meaningful domain events; event catalogue; ownership; process manager; coarser granularity | A small, well-documented set of domain events with a clear producer and consumer |
| `command-disguised-as-event` | Command disguised as event | A supposed event actually orders one specific consumer to perform an action. | apparent decoupling vs. semantics, `autonomy` | Make it an explicit command; publish a past fact instead; redraw ownership | An event with several real subscribers, even if one of them happens to be the "obvious" one |
| `event-as-rpc` | Event as RPC | The producer waits for an immediate reply to an event, recreating RPC indirectly. | technical decoupling vs. clarity, latency | Explicit RPC; recognised request/reply; real asynchronous workflow; callback | Fire-and-forget publication that merely logs an acknowledgment, without blocking on it |
| `integration-model-coupling` | Integration model coupling | Several systems share one large, frequently-changing integration model. | standardisation vs. `autonomy`, versioning | Per-consumer contracts; specific events; schema evolution; anti-corruption layers | A small, stable, rarely-changing shared contract (e.g. the OpenAPI types this repo already generates) |
| `orchestration-sprawl` | Orchestration sprawl | Process coordination is scattered across services, jobs, handlers, and consumers. | local `autonomy` vs. `comprehensibility`, global `robustness` | Process manager; explicit saga; state machine; explicit workflow ownership | A short, linear process with no branching or compensation that doesn't need a named owner |
| `retry-storm` | Retry storm | Several layers retry the same operation independently and amplify failures. | `resilience` vs. stability, `efficiency` | One retry policy; backoff; circuit breaker; idempotency; retry limits | A single, deliberate retry policy at one layer, with every other layer explicitly not retrying |
