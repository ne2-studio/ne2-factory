# Data and consistency smells

| id | Smell | Description | Attributes in tension | Candidate movements | Common false positive |
|---|---|---|---|---|---|
| `shared-database` | Shared database | Multiple modules or services read and write the same tables with no clear owner. | `consistency`, ease of querying vs. `autonomy`, `encapsulation` | Table ownership; APIs; events; views/materialised views; database per service where justified | A genuinely shared, append-only reference table (e.g. countries) that nothing meaningfully "owns" |
| `data-model-as-architecture` | Data model as architecture | The system's structure directly mirrors the database schema, and technical relationships drive the design instead of the domain. | simple persistence vs. domain `extensibility`, `encapsulation` | Separate domain model from persistence model; repositories; read models; explicit mappings | A genuinely simple domain where the table shape and the domain shape coincide for good reason, not by default |
| `chatty-data-access` | Chatty data access | One operation requires many small queries or calls, often because of a boundary placed too finely. | fine-grained `encapsulation` vs. `efficiency` | Coarse-grained APIs; batching; prefetching; aggregate queries; a purpose-built read model | A chatty pattern with no measured cost — N+1 shaped code that runs on a small, bounded N |
| `dual-write` | Dual write | One operation modifies two systems with no reliable atomicity or recovery mechanism. | availability, simplicity vs. `consistency`, `robustness` | Transactional outbox; inbox; idempotency; saga; reconciliation | Two writes where the second is a best-effort side effect (e.g. a metric) that's fine to lose |
| `unowned-derived-data` | Unowned derived data | Indexes, caches, projections, or duplicates exist with no owner and no rebuild strategy. | `efficiency` vs. `consistency`, `operability` | Explicit ownership; canonical source; rebuild procedure; invalidation; versioned events | A cache with a short, well-understood TTL and no correctness dependency on it being fresh |
| `implicit-eventual-consistency` | Implicit eventual consistency | The system is eventually consistent, but the UI, rules, or consumers assume immediate consistency. | availability, decoupling vs. `comprehensibility`, user experience | Make the pending state explicit; versioning; compensation; progress UX; read-your-writes | A delay short and reliable enough that no user or rule has ever observed the inconsistent window |
| `god-query` | God query / universal read model | One read model tries to serve every screen, consumer, and use case. | reuse, `consistency` vs. `efficiency`, independent evolution | Read models per use case; light CQRS; purpose-built projections | A shared read model with genuinely identical needs across its few consumers today |
