# Domain model smells

| id | Smell | Description | Attributes in tension | Candidate movements | Common false positive |
|---|---|---|---|---|---|
| `missing-domain-concept` | Missing domain concept | A relevant business idea exists only implicitly — in conditionals, scattered naming, or convention — with no representation of its own. | structural simplicity vs. `domain-explicitness`, `comprehensibility` | Introduce a value object, policy, entity, aggregate, domain service, or explicit module | A concept that has data but no rules, identity, or invariant — naming it would add a wrapper, not knowledge |
| `anemic-domain-architecture` | Anemic domain architecture | Rules live in procedural services while entities and aggregates are plain data containers. | technical separation vs. `encapsulation`, invariant protection | Move behaviour onto the model; introduce aggregates; encapsulate state changes; remove public setters | CRUD-shaped data with genuinely no business rule attached — a data container is the correct shape there |
| `primitive-obsession-architectural` | Primitive obsession (architectural) | A relevant concept travels across the whole system as a string, id, boolean, or dictionary with no shared semantics. | interoperability, simplicity vs. `robustness`, `comprehensibility` | Value objects; specific types; semantic contracts; parse at the boundary | Wrapping every primitive with no concrete invariant to enforce |
| `leaky-domain-boundary` | Leaky domain boundary | One bounded context directly uses another context's entities, internal state, or rules. | reuse vs. `autonomy`, local `consistency` | Own DTOs; anti-corruption layer; explicit model translation; integration events | Two contexts sharing a genuinely stable, versioned public contract designed for that purpose |
| `generic-domain-model` | Generic domain model | The system uses generic abstractions like `Item`, `Entity`, `Manager`, or `Process` to represent genuinely different concepts. | generic reuse vs. `domain-explicitness` | Specialise the types; separate contexts; introduce ubiquitous language; replace generic inheritance with composition | A genuinely generic technical concern (e.g. an audit log entry) that has no domain meaning to specialise into |
| `multiple-representations-without-ownership` | Multiple representations without ownership | The same concept has more than one representation, with no clear canonical one and no explicit translator between them. | local `autonomy` vs. `consistency`, `comprehensibility` | Define ownership; per-context models; explicit mappers; versioned contracts | Deliberately different read models serving genuinely different consumers, with a known mapping between them |
| `domain-logic-leakage` | Domain logic leakage | Business rules appear in controllers, jobs, UI, SQL, pipelines, or scripts instead of the domain layer. | local convenience vs. `consistency`, `testability` | Centralise the policy; application/domain service; specification; invariant enforcement at one point | A UI-only validation (e.g. required-field hinting) that has no independent business meaning beyond the form |
| `aggregate-boundary-mismatch` | Aggregate boundary mismatch | The aggregate is too large, too small, or doesn't match the actual transactional invariant it should protect. | `consistency` vs. concurrency, performance, `autonomy` | Redraw the aggregate; separate immediate from eventual consistency; domain events; process manager | An aggregate that's large but every field inside it genuinely participates in one invariant |

## Notes

### `missing-domain-concept`

A domain abstraction is justified when it captures knowledge, not merely data. Do not create domain objects for passive data with no behaviour; do not wrap every primitive without a concrete invariant; do not build a full domain layer for what is genuinely CRUD.
