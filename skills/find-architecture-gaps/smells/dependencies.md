# Dependency and abstraction smells

| id | Smell | Description | Attributes in tension | Candidate movements | Common false positive |
|---|---|---|---|---|---|
| `abstraction-leakage` | Abstraction leakage | Consumers must understand the internal details of an abstraction to use it correctly. | `reusability` vs. `efficiency`, control | Redesign the contract; raise the semantic level; encapsulate configuration; remove the abstraction if it's beyond repair | An abstraction that intentionally exposes a low-level knob for the rare caller who needs it, documented as such |
| `speculative-generality-architectural` | Speculative generality (architectural) | Layers, plugins, events, or contracts are introduced for scenarios that don't exist yet. | future `extensibility` vs. `comprehensibility`, current cost | Collapse layers; inline; remove interfaces; defer the abstraction until real evidence appears | Genuine platform code with more than one real, current consumer already depending on the generality |
| `premature-platformization` | Premature platformization | A local capability is turned into a framework, platform, or shared service too early. | future `reusability`, `scalability` vs. velocity, contextual `cohesion` | Fold back into local integration; extract gradually; only productise after multiple real consumers exist | A capability with genuinely more than one real consumer today, not a hoped-for future one |
| `pass-through-architecture` | Pass-through architecture | Several layers only forward the same data and calls without adding policy or translation. | structural uniformity vs. `comprehensibility`, simplicity | Collapse layers; remove empty facades; allow controlled direct access | A layer that's currently pass-through but exists at a genuine, already-used seam (e.g. the only place auth is checked) |
| `interface-explosion` | Interface explosion | Every implementation gets its own interface, or numerous trivial single-use contracts exist. | theoretical `substitutability` vs. `comprehensibility`, navigability | Remove accidental interfaces; introduce them only at real boundaries; use concrete types or functions | An interface at a genuine seam with more than one real implementation, or one crossing a real deployability boundary |
| `wrong-abstraction` | Wrong abstraction | Different cases are forced under one common abstraction, producing flags, exceptions, and growing conditionals. | `reusability` vs. `cohesion`, clarity | Duplicate temporarily; split the abstraction; composition; replace inheritance; split the interface | Cases that are currently identical and have never diverged — premature splitting here is its own smell |
| `vendor-leakage` | Vendor leakage | Types, errors, or capabilities from a third-party provider travel through the domain or application layer. | leveraging the provider vs. `substitutability`, `testability` | Adapter; anti-corruption layer; own models; encapsulate the SDK | A thin, intentional wrapper module that's the one and only place vendor types are allowed, by design |
| `temporal-coupling` | Temporal coupling | Components must be invoked in a specific order that isn't expressed by their contracts. | component flexibility vs. `robustness`, `comprehensibility` | Encapsulate the workflow; state machine; pipeline; types that represent state; transactions | An order that's naturally sequential (e.g. read before write) and would be reflected by any correct contract |
